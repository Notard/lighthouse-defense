# 루프 엔지니어링: 여러 에이전트로 만드는 구조

> 사용자 (2026-10-20): "본격적인 개발은 이렇게 나눠서 하고 루프 엔지니어링 개념을 네가 조사해와서 여러 에이전트가 일하고 루프 엔지니어링으로 하는 구조로 가자." (역할 표 함께)

## 루프 엔지니어링이란 (조사 요약)

- **정의**: 에이전트에게 매번 프롬프트를 쓰는 대신, 에이전트가 **계획 → 변경 → 결과 관찰 → 고침**을 반복해 일을 끝내도록 그 반복 구조(도구, 상태, 검증, 끝내는 조건, 사람이 끼어드는 지점)를 설계하는 일. 프롬프트(무엇을 물을지) → 컨텍스트(무엇을 알려 줄지) → 하네스(에이전트 하나가 안전하게 일할 환경) 위의 한 층으로, "하네스가 작업장이면 루프는 그 작업장을 돌리는 운영 방식" ([Kilo](https://kilo.ai/articles/what-is-loop-engineering), [IBM](https://www.ibm.com/think/topics/loop-engineering), [SK AX 요약](https://www.skax.co.kr/insight/trend/3840))
- **공통으로 강조하는 것** ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering) 체크리스트·안티패턴 등)
  1. **검증 가능한 끝내는 조건**: "테스트가 모두 통과하면 멈춤"처럼. 모호하면 루프가 끝나지 않고 비용이 커진다
  2. **만든 쪽과 확인하는 쪽을 나눈다** (maker/checker): 자기 결과를 스스로 채점하면 너그럽다. 확인하는 쪽의 기본값은 **거절**
  3. **자동 관문**: 테스트·분석·빌드·범위 검사가 통과해야 다음으로
  4. **시도 횟수 상한** (예: 3번) → 넘으면 상태를 적고 사람에게
  5. **상태 파일**: 모델은 실행이 끝나면 잊지만 디스크의 기록은 남는다. 매 바퀴 처음에 읽고 끝에 쓴다, 해결된 것은 지운다. 실행 기록은 덧붙이기만
  6. **범위 제한**: 고칠 수 있는 경로 목록·금지 목록, 한 번에 바꾸는 파일 수 상한, 작업마다 따로 쓰는 작업 공간(git worktree)
  7. **정지 스위치**와 **단계적 자율성**: 보고만 → 확인이 붙은 작은 자동 수정 → 무인. 확인하는 쪽이 한동안 믿을 만했을 때만 다음 단계로
- **함정**: 같은 에이전트가 구현·검증을 다 함, 상한 없이 "초록불 될 때까지", 테스트에만 맞춘 구현(테스트 과적합), 오래된 가정, 이해 부채(테스트는 통과하는데 아무도 모르는 코드), "다 됐다"는 주장일 뿐 증명이 아님

## 이 프로젝트의 역할

| 에이전트 | 맡는 일 | 고칠 수 있는 곳 | 손대면 안 되는 것 | 모델 |
|---|---|---|---|---|
| **implementer** | 작업 카드대로 구현, 표 → 코드 변환기 | `lib/`, `tools/`(밸런스·루프 도구 제외), `assets/`, `web/`, `windows/`, `art/` | `test/`, `docs/`, `data/` | **Codex** (gpt-5.6-sol, ChatGPT OAuth, 카드 011부터) |
| **tester** | 사람이 쓴 테스트 표 → 테스트 코드 | `test/`만 | 구현 코드, 기대값 | Sonnet 5.5 |
| **balancer** | 밸런스 시뮬레이터, `balance/balance.csv` | `tools/balance/`, `test/balance/`, `balance/` | `data/tables/` 숫자 (제안만) | Sonnet 5.5 |
| **reviewer** | 인수 조건과 대조, 보고만 | 없음 (읽기만) | 모든 파일 | Opus 5.5 |
| **리드** (메인 대화) | 표 쓰기, 일 나누기, 관문 실행, 판단, 커밋·푸시, 사용자와 대화 | `docs/`, `data/tables/`, `loop/` 등 전부 | — | — |

정의: `.claude/agents/*.md`. 범위 표(기계용): `loop/roles.json`.

## 사람이 쓰는 것 (리드)

| 파일 | 내용 |
|---|---|
| `docs/design.md` | 게임 규칙의 정답. 기능마다 절 하나 |
| `docs/tests/<기능>.md` | **테스트 표**: 번호, 상황(주어진 것), 행동, 기대값. tester가 그대로 코드로 |
| `docs/acceptance/<기능>.md` | **인수 조건**: 사용자가 보기에 "됐다"의 목록. reviewer가 대조 |
| `data/tables/*.csv` | 숫자 표 (친구·적·카드·웨이브·밤). 코드는 표에서 읽는다 |
| `loop/tasks/<번호>-<이름>.md` | 작업 카드: 목표 한 문장, 하지 않을 것, 관련 문서, 끝내는 조건, 맡을 에이전트 |
| `loop/STATE.md` | 지금 상태: 진행 중, 사람 기다림, 지켜볼 것, 마지막 실행 |
| `loop/run-log.md` | 바퀴마다 한 줄 이상 덧붙이기만 (누가, 무엇을, 관문 결과, 판정) |

## 한 바퀴 (기능 하나)

```
 리드: 설계 절 + 테스트 표 + 인수 조건 + (숫자 표) + 작업 카드
   │
   ▼
 tester ── 테스트 표 → test/ (아직 구현이 없어 실패 = 빨간 불)
   │        관문: 범위(tester), 표의 모든 번호가 테스트로
   ▼
 implementer ── lib/ 구현 → 테스트 통과 (최대 3번 시도)
   │        관문 1 analyze·test, 관문 2 범위(implementer), 관문 3 웹 빌드
   ▼
 (밸런스가 걸린 기능) balancer ── 시뮬레이터 → balance.csv, 제안
   │        리드가 제안을 보고 data/tables를 직접 고칠지 판단
   ▼
 reviewer ── 인수 조건·테스트 표·설계와 대조 → 승인/거절 (기본 거절)
   │
   ▼
 리드 판단 ── 승인 + 관문 통과 → 문서(TODO·WORKLOG·preview) → 커밋·푸시 → 다음 카드
              거절 → 무엇이 틀렸는지 카드에 적어 해당 에이전트에게 다시 (같은 카드 최대 3바퀴)
              3바퀴를 넘거나 판단이 필요한 일(규칙·재미·그림) → 사용자에게
```

- **관문 실행**: `bash tools/loop/check.sh <역할> [--base main]` (분석 + 테스트 + 범위 + 웹 빌드)
- **작업 공간**: 구현·테스트 에이전트는 따로 git worktree에서 일하게 할 수 있다 (`Agent` 도구의 `isolation: worktree`). 결과 브랜치를 `--base main`으로 관문에 통과시킨 뒤 리드가 합친다. 작은 일은 같은 작업 트리에서 차례로
- **끝내는 조건**: 카드의 "끝내는 조건"이 모두 참 + 관문 통과 + reviewer 승인. 화면·재미처럼 테스트로 판정할 수 없는 것은 단계 끝에 **사용자 확인**
- **상한**: implementer 시도 3번 / 카드 하나에 바퀴 3번 / 한 번에 바꾸는 파일 30개 (`roles.json`의 `maxFiles`)
- **정지**: `loop/STATE.md` 맨 위 `정지: 예`면 리드는 새 바퀴를 시작하지 않는다 (사용자가 "멈춰" 하면 리드가 적는다)
- **자율성 단계**: 처음에는 단계(plan.md)마다 사용자 확인 → reviewer 판정이 믿을 만해지면 작은 카드는 리드가 바로 커밋

## 숲 지키기에서 배운 것을 관문으로

| 숲 지키기에서 겪은 일 | 여기서는 |
|---|---|
| 플러그인을 더한 뒤 증분 빌드가 예전 등록 파일을 씀 | 플러그인을 더한 카드는 `flutter clean` 뒤 관문 |
| Flame의 add는 다음 프레임 → 같은 프레임에 띄우고 닫은 판이 남음 | reviewer 점검 목록 6번 |
| 릴리스 빌드에서만 `Curve.transform(t>1)` 무한 루프 | 효과 곡선 입력은 0~1로 묶기 (설계 원칙) |
| 테스트 기대값을 구현 쪽이 맞춰 바꾸는 유혹 | 테스트·기대값은 tester·리드만 |
| 밸런스 숫자를 감으로 | 봇 결과(balance.csv)와 목표 표로 |

## implementer를 Codex로 (2026-10-20, 사용자: "에이전트를 codex oauth 로 하자" → "implementer만 Codex")
- 리드가 지시를 `logs/codex/<이름>.md`(지시 파일, gitignore)에 쓰고 `python tools/loop/codex_implementer.py <지시 파일>`
- 실행기는 역할 설명(`.claude/agents/implementer.md` 본문) + `CLAUDE.md` + 지시를 `codex exec -s workspace-write`에 넘긴다
- 안전 관문: 실행 앞뒤 HEAD·stash·스테이징 비교 (바뀌면 종료 3). **Codex가 도는 동안 리드는 커밋하지 않는다** (오탐이 난다)
- 끝나면 `gate.py implementer` 범위 검사와 Codex 보고(`logs/codex/<시각>-report.md`). 그 뒤는 전과 같다: 리드 관문 → reviewer(Claude)
- 샌드박스는 다른 Windows 사용자(CodexSandboxOffline)로 돈다: flutter 캐시 폴더 쓰기 허용과 git safe.directory 환경 변수를 실행기가 준다
- tester·reviewer·balancer는 Claude 그대로 (만든 쪽과 검사하는 쪽의 모델이 달라 서로의 실수를 더 잘 잡는다)
